現在の受付を止めずに、新しいバックエンド（`gas/Code.gs`）へ切り替えるための手順です。
**受付スプレッドシートの列・並びは今のまま変わりません。**

## 最新版（v2.1）への更新手順

v2.1 で入ったもの：残り枠とキャンセル待ち／「次の開催をはじめる」の一括処理／
受付シートの見出しの自動追加／データベースを見出しの名前で書き込む仕組み。

**GAS を先に更新してから、申込フォーム・管理画面（main）を公開してください。**
（順番が逆でも事故にはなりません。GASが古いうちは、満枠のブースはこれまでどおり選べないままで、
キャンセル待ちや残り枠の表示は出ません）

1. `gas/Code.gs` を貼り付けている Apps Script プロジェクトを開き、中身を最新の `gas/Code.gs` に貼り替えて保存
2. 「デプロイ」→「デプロイを管理」→ 鉛筆マーク →「バージョン: 新バージョン」→「デプロイ」
   （**URLは変わりません**。「新しいデプロイ」ではなく「デプロイを管理」から行ってください）
3. `gasUrl?action=status` をブラウザで開き、`"version":"2.1.0"` になっていることを確認
4. main に取り込む（申込フォームと管理画面が新しくなります）
5. 管理画面を開き、上に「今回の受付シート」の警告が出ていたら、
   **「第◯回の受付シートを作る」**を押す（→「6. 次の開催をはじめるとき」）

データの移し替えは不要です。受付シートには次の申込のときに「ステータス」列が右端に増えます。

## 1. 新バックエンドを別プロジェクトとして用意する（受付は止まりません）

1. [script.google.com](https://script.google.com/) を開き、**新しいプロジェクト**を作成
   （名前の例: `ぶち癒しフェスタ申込フォーム v2`）
2. 既定の `コード.gs` の中身を全消しして、このリポジトリの **`gas/Code.gs`** を貼り付け
3. 保存

`gas/appsscript.json` の編集は不要です。中身は新規プロジェクトの初期値と、
デプロイ画面で選ぶ内容（自分として実行 / 全員がアクセス可）と同じものです。
タイムゾーンを確認したい場合だけ「⚙️ プロジェクトの設定」を開き、
`(GMT+09:00) 日本標準時` になっていることを見てください。

> 現行プロジェクトはそのまま動かし続けます。切り替えは手順5で行います。

### `CONFIG_JSON_URL` について

`gas/Code.gs` の先頭にあるこの1行が、設定の読み込み元です。**変更する必要はありません。**

```js
const CONFIG_JSON_URL = 'https://bayashichan.github.io/buchiiyashifestaodawara/apply/config.json';
```

移行に必要な設定（`databaseSpreadsheetId` / `event.editionId`）は
2026年8月20日に main へ取り込み済みで、このURLから読み込めます。

> **「databaseSpreadsheetId がありません」というエラーが出た場合**
>
> 設定は最大30分キャッシュされます。まず **`clearConfigCache` を1回実行**してから、
> あらためて実行してください。
> それでも解消しない場合は、上のURLをブラウザで開き、
> `databaseSpreadsheetId` が含まれているかを確認してください。

## 2. 動作確認（書き込みは発生しません）

エディタ上部の関数選択から実行します。初回は権限の承認が求められます。

1. **`testReceptionColumnMapping`** を実行 → 実行ログを開く
   受付シートの1列目から順に「列名 → 入る値」が表示されます。
   ここで **すべての列が正しい位置に入ること** を必ず確認してください。
   （※ この関数はシートに書き込みません）
2. 気になる列があれば、そのままご連絡ください。

## 3. データベースを整える

`apply/config.json` には次が設定済みで、すでに公開されています。

```json
"event":  { "edition": "第1回", "editionId": "odawara-01" },
"databaseSpreadsheetId": "1QjOHkZRXZOJF7e6pslNPO2S_rnnHXaUxhY_LJrH9D6M"
```

GAS エディタで順に実行してください。

1. **`setupDatabase`**
   - DB用スプシの既存シートを `_backup_日付_元のシート名` に改名して非表示にします（**データは消えません**）
   - `applications` / `exhibitors` / `events` の3シートを作成します
2. **`migrateReceptionToDatabase`**
   - 現在の受付スプシの全行を、第1回のデータとして `applications` に取り込みます
   - 同じ（開催回ID＋メール＋申込日時）は二重登録されないので、**受付中に何度実行しても大丈夫**です
   - 実行ログに「◯件を登録、◯件をスキップ」と出ます

詳しい列の意味は [`DATABASE.md`](./DATABASE.md) を参照してください。

### すでに `odawara-01` で取り込み済みの場合

管理画面の作り直しにあわせて、開催回の記録用キーを「第1回」に統一しました。
`odawara-01` として登録済みの行が残っていると、同じ回のデータが2つに分かれてしまいます。

GAS エディタで **`renameEditionId`** を1回実行してください
（関数の中の `OLD_ID` / `NEW_ID` が `odawara-01` → `第1回` になっていることを確認してから実行）。
実行ログに「開催回IDを付け替えました」と出れば完了です。

## 4. テスト送信

1. GAS を **ウェブアプリとしてデプロイ**
   - 「デプロイ」→「新しいデプロイ」→ 種類: **ウェブアプリ**
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**
   - 発行された `/exec` URL を控える
2. ブラウザで `発行されたURL?action=status` を開き、次を確認
   - `receptionSheetFound: true` … 受付シートが見えている
   - `databaseSheetFound: true` … DBが見えている
   - `editionId` が `odawara-01` になっている
3. GAS エディタで **`testDoPost`** を実行
   - 受付シートとDBに1行ずつテスト行が入ります
   - **列ズレが無いことを確認したら、両方のテスト行を削除**してください

## 5. 切り替え

`apply/config.json` の `gasUrl` を、手順4で発行した新しい `/exec` URL に書き換えます。

- 管理画面（`admin/config-editor.html`）の「🔧 インフラ設定 → GAS デプロイURL」を書き換えて
  「🚀 保存して公開する」を押すのが簡単です
- 反映まで1〜2分。反映後、**実際のフォームから1件テスト申込**をして、
  受付スプシとDBの両方に入ることを確認してください

### 元に戻したいとき

`gasUrl` を元のURLに戻すだけで、旧バックエンドに戻ります。
（旧プロジェクトは消さずに残しておいてください）

### 受付シートには入るのに、データベースに入らないとき

**`gasUrl` が古いデプロイ（v1）を指しています。** DB保存はv2の機能で、
v1は受付シートへの保存とメール送信しかしません。

確認は `gasUrl?action=status` をブラウザで開くだけです。

| 返ってきた内容 | 意味 | 対処 |
| --- | --- | --- |
| `"version":"1.0.0"` など、v2以外 | 旧プロジェクト／旧デプロイを見ている | 下の手順で差し替え |
| `"version":"2.0.0"` で `databaseSheetFound:false` | DBスプシを開けていない | `databaseSpreadsheetId` と閲覧権限を確認 |
| `"version":"2.0.0"` で `databaseSheetFound:true` | 経路は正常 | GASの「実行数」で `doPost` のログを確認 |

**差し替え手順**

1. `gas/Code.gs` を貼り付けた Apps Script プロジェクトを開く
2. 「デプロイ」→「新しいデプロイ」→ 種類: ウェブアプリ
   （実行するユーザー: **自分** ／ アクセスできるユーザー: **全員**）
3. 発行された `/exec` URL をコピー
4. 管理画面を `?setup` 付きで開き、「GAS ウェブアプリURL」に貼って保存
5. もう一度 `?action=status` を開き、`version` が `2.0.0` になったことを確認

> **GASの「実行数」に `doPost` が出てこない場合**、そのプロジェクトはフォームから
> 呼ばれていません。＝`gasUrl` が別のプロジェクトを指している、ということです。
> コードを貼り替えただけでは `/exec` の中身は変わりません。既存デプロイを更新するなら
> 「デプロイを管理」→ 鉛筆マーク →「バージョン: 新バージョン」→ デプロイ が必要です。

すでに受付シートにだけ入ってしまった申込は、GASエディタで
**`migrateReceptionToDatabase()`** を実行すればDBへ取り込めます（重複しません）。

## 6. 次の開催をはじめるとき

管理画面の「📅 イベントのこと」を開くと、いちばん上に
**「🆕 次の開催をはじめる」** があります。ここから進めれば、受付シートの作成から保存までが一度に行われます。

### 手順

1. 「🆕 次の開催をはじめる」の **「はじめる」** を押す
2. 入力欄を確かめる
   - **開催回** … 「第3回」のように次の回が最初から入っています（前回と同じ名前は使えません）
   - **イベント名** … 次の回の名前に置き換わった状態で入っています
   - **開催日時** … 新しい日程を入れてください（空のままなら前回の日時のまま）
   - **会場** … 前回のものが入っています。変わる場合だけ直してください
3. **「この内容ではじめる」** を押す → 確認のパネルが出て、何が行われるかが一覧で表示されます
4. 内容を確かめて **「はじめる」** を押す → 次の4つが順番に進み、それぞれに ✅ が付きます
   1. 受付シートを作る（前回の受付シートと**同じフォルダ**に、**同じ見出し**で作られます）
   2. 設定に反映する
   3. 保存する
   4. 申込フォームに反映する（1〜2分。ここはパネルを閉じても大丈夫です）

> **受付シートを作れなかったときは、何も変わりません。**
> 「開催回だけ変わって、受付シートは前の回のまま」という状態にはなりません。
> パネルに「別の画面で作る」が出るので、それを押してシートを作り、表示されたURLを貼り付けると続きが進みます。
> 「バックエンド（GAS）が古いため」と出た場合は、GASを最新版にしてからやり直してください。

### 受付シートが前の回のままになっていたら

管理画面の上に **「⚠️ 今回（第◯回）用の受付シートがまだありません」** という警告が出ます
（開催回の欄だけを書き換えて保存した場合など）。

- **「第◯回の受付シートを作る」** … 今回の受付シートを作って、保存まで行います
- **「いまのシートのまま使う」** … いまのシートを今回の受付シートとして使います（「設定内容を保存」で確定）

### 自動で行われること

- すべてのブースを「受付中」に戻す（手動で締め切ったブースも再開。残り枠は新しい受付シートで0から数え直します）
- 「前回の内容を呼び出せるようにする」をONにする

どちらもチェックを外せば行いません。

### そのまま引き継がれるもの（設定不要）

**出展者データベース／写真の保存フォルダ／料金・ブース・定員／質問／規約／メールの文面**

写真は、親フォルダの下に開催回の名前でフォルダが自動作成され、その中に保存されます
（例: `写真フォルダ/第2回/`）。

> **「データの保存先」は、運用する方がさわる必要はありません。**
>
> - **受付シート** … 「次の開催をはじめる」で自動的に作られ、URLも自動で入ります
> - **写真の保存フォルダ** … 最初の設定のまま。開催回ごとのフォルダは自動で作られます
> - **出展者データベース** … 最初の設定のまま。全開催分がここにたまります
>
> 手で入れ直すのは、フォルダやシートを引っ越したときだけです。

前の回の申込は `applications` にそのまま残り、新しい回のデータが追記されていきます。

### 取り込みが途中で止まったとき

GAS には1回の実行が6分までという制限があります。申込件数が多いと
`migrateReceptionToDatabase` が途中で止まり、次のような状態になることがあります。

- `applications` に入っていない申込がある
- 申込は無いのに `exhibitors` にだけ名前が残っている
- `出展回数` が実際より多い

直し方は2手順です。

1. **`migrateReceptionToDatabase`** をもう一度実行する
   → 入っていない申込だけが追加されます（重複はしません）
   → 実行ログの「◯件を登録」が 0 になるまで繰り返してください
2. **`rebuildExhibitors`** を実行する
   → `applications` を正として `exhibitors` を数え直します
   → 申込が無い人の行は消え、`出展回数` が正しくなります
   → 出展者IDと「スタッフメモ」は引き継がれます

`rebuildExhibitors` は何度実行しても同じ結果になります。
`testDoPost` のテスト行が残っている場合も、これで取り除かれます。

### 開催後にやること（任意）

座席番号・入金状況・ステータス（キャンセル・繰り上げなど）を受付スプシで直したあと、
GAS で **`syncReceptionUpdatesToDatabase`** を実行すると、その内容がDB側にも反映されます。
（入金確認が入っている行は「入金済」になります。キャンセルの行はキャンセルのままです）

## 7. 残り枠とキャンセル待ち

### 設定（管理画面の「🏪 ブース（出展枠）」）

いちばん上の **「満枠のブースは『キャンセル待ち』で受け付ける」**（最初はオン）

- オン … 満枠のブースも選べます。申込は「キャンセル待ち」として記録され、専用の自動返信メールが届きます
- オフ … 満枠のブースは選べません。申込も受け付けません

ブースをタップすると、ブースごとの設定がひらきます。

| 設定 | 内容 |
|---|---|
| 残り枠を数える | オンにすると申込の数を数え、定員に達したら自動で満枠に切り替わります |
| 定員 | 何枠まで受け付けるか（−／＋ で変えられます） |
| フォームに「残りあと◯枠」を出す | オフにすると数は出さず、裏で数えるだけになります |
| 表示しはじめるタイミング | 「いつも出す」か「残りが少なくなってから出す（◯枠以下で）」 |
| 手動で締め切る | 空きがあっても満枠として扱います |

設定欄の中に「フォームではこう見えます」という見本が出るので、確かめながら設定できます。

### 数え方

- **今回の受付シート**で、そのブースの申込を数えます
- 「ステータス」列に **「キャンセル」を含む行（キャンセル・キャンセル待ち）は数えません**
- 満枠かどうかは、申込を書き込む直前に数え直して決めます。同時に申込があっても定員を超えません
- 残り枠はブース名で数えています。**受付中にブース名を変えると、0から数え直しになります**

### 運用のしかた（受付シートの「ステータス」列）

| したいこと | 受付シートでの操作 |
|---|---|
| キャンセルが出た | その人の「ステータス」を **`キャンセル`** に書き換える（1枠空きます） |
| キャンセル待ちの人を繰り上げる | 「ステータス」を **`申込`** に書き換えて、事務局からその方へ連絡する（振込の案内など） |

- キャンセル待ちの申込では、事務局への通知メールの件名の先頭に **【キャンセル待ち】** が付きます
- キャンセル待ちの方へのメールの文面は「✉️ 自動返信メール」の下のほうで変えられます（振込の案内は入れないでください）
- 繰り上げの連絡は、今のところ手動です

### 受付シートの見出し

- 申込は**見出しの名前**で書き込みます。列を並べ替えても正しい列に入ります
- 質問を増やしたときなど、足りない見出しは**右端に自動で追加**されます（保存して1〜2分後、または次の申込のとき）
- フォームで集めている項目の列を消すと、右端に戻ってきます。いらない列は「削除」ではなく「非表示」にしてください

## 8. 管理画面の使い方

URL: `https://bayashichan.github.io/buchiiyashifestaodawara/admin/config-editor.html`

スマホでもそのまま使えます。設定画面はこの1つだけです
（以前の `quick-settings.html` は、この画面へ案内するだけのページになりました）。

### クライアントの使い方

1. URLを開く
2. **合い言葉**を入力する（初回だけ。以後その端末では省略されます）
3. 変えたいところを直して、下の **「設定内容を保存」** を押す

保存すると1〜2分で申込フォームに反映されます。

**申込フォームのURL**は、画面のいちばん上の「🔗 申込フォームのURL」にあります。
「📋 URLをコピー」を押すと、LINEのリッチメニューやSNSにそのまま貼れます。
LINE連携（LIFF）を設定している場合は、LINEアプリ用のURLも表示されます（リッチメニューにはこちらがおすすめです）。
接続の設定やファイルのダウンロードは表示されないので、迷う場所はありません。

### 質問の並び順を変える

「↕️ 質問の並び順」をひらくと、申込フォームに出る順番どおりに項目がならんでいます。

- **▲ ▼** を押すと1つずつ動きます。押した項目は指の下に残るので、同じ場所を続けて押せばどんどん動きます
- 左の **≡** を指で押さえたまま上下に動かすと、離したところに入ります（画面の上下の端まで持っていくと、画面も動きます）
- 色つきの帯は**見出し**です。見出しも動かせますし、質問を別の見出しの下へ移すこともできます
- 「いまは表示しない」と出ている項目は、フォームには出ません（オンにすると、その位置に出ます）
- 中に何もない見出しはフォームに出ません。見出しの番号（1. 2. 3.…）は自動で振り直されます
- 「はじめの並び順にもどす」で元に戻せます

並べ替えても、受付シートの列の並びや、送られてくる内容は変わりません
（自動返信メールに差し込む「自由な質問」の答えは、フォームと同じ順番になります）。
並び順は `apply/config.json` の `formOrder` に保存されます。

### 作成者の初期設定（1回だけ）

URLの末尾に `?setup` を付けて開くと、「🔒 作成者用」の欄が現れます。

```
https://bayashichan.github.io/buchiiyashifestaodawara/admin/config-editor.html?setup
```

ここで次を入力し、「合い言葉を登録する」を押します。

- GitHub ユーザー名 / リポジトリ名
- アクセストークン（Fine-grained・このリポジトリのみ・**Contents: Read and write**）
- **GAS 管理トークン**（任意）… GASのスクリプト プロパティに `ADMIN_TOKEN` を
  設定している場合だけ。受付シートの作成やキャッシュクリアに使います
- 合い言葉（**10文字以上**）

トークンは合い言葉で暗号化され、`admin/unlock.json` として保存されます。
以後はどの端末でも、合い言葉だけで管理画面をひらけます。

> **合い言葉の扱い**
> 暗号化されたファイル自体は誰でもダウンロードできる場所にあります。
> 安全性は合い言葉の強さに依存するため、短い言葉や推測しやすい言葉は避けてください。
> 漏れた疑いがあるときは、GitHub でトークンを失効させてから登録し直してください。

作成者用の欄には、`config.json` の公開URL・GASのURL・Worker のURL も入っています。
通常のURLで開いた場合はこの欄ごと表示されないため、クライアントが触ることはありません。

### メール文面の書き方

「📧 自動で送るメール」の本文欄では、差し込み項目が**色つきのタグ**で表示されます。

```
[お名前] 様
この度は [イベント名] へのお申込みありがとうございます。
```

- 入れたい場所をタップしてから、上のボタン（**＋ お名前** など）を押します
- タグは**ひとかたまり**なので、消すときは1回の削除でまとめて消えます
- 送信時に、その人の情報へ自動で置き換わります
- タグ以外の文章は、ふつうに打ち替えて構いません

### 反映のタイミング

1. 保存 → GitHub の `apply/config.json` が更新される
2. 1〜2分で申込フォームに反映される（画面下に「✅ 申込フォームに反映しました」と出ます）
3. 反映を確かめてから、バックエンド側の一時保存が自動でクリアされます。
   このとき、質問を増やした場合などは受付シートの見出しも追加されます

画面を閉じてしまって手順3が行われなかった場合も、バックエンドは5分以内に新しい設定を読み直します。

## 補足: 写真が送れなかった申込について

出展者の端末や画像によっては、写真の送信に失敗することがあります。
その場合でも**申込自体は完了**し、次のように処理されます。

1. 申込完了画面に「公式LINEあてに出展名と写真をお送りください」という案内が出る
   （`config.json` の `lineOfficialUrl` を設定しておくと「公式LINEを開く」ボタンも表示されます）
2. 自動返信メールの冒頭に、同じお願いの文面が入る
3. 受付シートとデータベースの「プロフィール写真」欄が **`LINE送付待ち`** になる
4. 事務局への通知メールの写真URL欄が **`⚠️ 未受領`** になる

受付シートで「LINE送付待ち」を検索すれば、写真待ちの方を一覧できます。
写真が届いたら、Drive に保存してそのURLを同じ欄に貼り替えてください。

申込者が最初から「写真をあとから公式LINEで送る」を選んだ場合も同じ扱いです。

### 写真の大きさについて

**サイズ制限はありません。** 写真を選んだ時点で自動的に縮小してから送ります
（長辺1200px以下・送信データが約1MB以下になるまで段階的に縮小）。

以前は8MBを超える写真を「縮小する前に」拒否していました。
最近のスマホの写真は8MBを超えることが珍しくないため、これが
「写真が送れない」原因になっていた可能性があります。

> 自動返信メールの文面に `{{photoNotice}}` と書いておくと、その位置に案内が入ります。
> 書かなかった場合は本文の先頭に自動で追加されます。

## 補足: 今回あわせて直した不具合

- **SNSリンクの2件目以降が送信されていなかった**
  「＋ SNSリンクを追加」で増やした欄に判定用のクラスが付いておらず、
  送信時の収集対象から漏れていました。
- **管理画面から保存すると日本語が文字化けする**
  `quick-settings.html` の Base64 変換が UTF-8 に対応しておらず、
  保存するとイベント名・規約・メール文面が壊れる状態でした。
  （このため、これまで満枠切り替えを保存していた場合は、
  一度 `apply/config.json` の中身を確認してください）
- **受付シートの列ズレの危険**
  旧バックエンドは設定の増減でヘッダー行を書き換える作りでした。
  新バックエンドは**既存のヘッダーを読み取って、その並びに合わせて書き込む**ため、
  スタッフが追加した列やラベル無しの列（懇親会人数など）を壊しません。
- **データベースの列を並べ替えると、別の列に入ってしまう（v2.1で修正）**
  データベースへの書き込みが決まった列の順番どおりだったため、並べ替えると値がずれていました。
  いまは受付シートと同じく**見出しの名前で書き込む**ため、並べ替えても正しい列に入ります。
- **保存直後に古い設定をバックエンドが覚えてしまうことがある（v2.1で修正）**
  保存した瞬間にバックエンドの一時保存を消していたため、公開が終わる前の古い設定を
  最大30分使い続けることがありました。いまは公開を確かめてから消し、一時保存も5分に短くしました。
